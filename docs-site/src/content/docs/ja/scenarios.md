---

各ルートは**特定の 1 つのことを起こす**ために存在します。
このページはその「なぜ」を書いたものです ― パスの一覧表では運べない部分です。

## パスを直書きせず、型付きヘルパーを使う

利用側で `/fails-then-succeeds?failTimes=2&key=x` を直書きすると、meadow 側の変更が
**数か月後に、誰も見ていないリポジトリで、静かに**その利用側を壊します。
`scenarios` エクスポートが、これらの URL が書かれている唯一の場所です。

```ts file="src/scenarios.ts#scenarios"
```

オリジンを前置して使います。

```ts
import { scenarios } from "meadow";

const url = `http://${meadowIp}:8080` + scenarios.failsThenSucceeds(2, "retry-budget");
```

## 静的なページ

### `/plain-html` ― 成功のベースライン

スクリプトもサブリソースも無い、素の 200 HTML。
他のシナリオは「動くと分かっているもの」と比べて初めて意味を持ちます。
テストが落ちたとき、`/plain-html` が
**「基盤が壊れているのか、そのシナリオが仕事をしているのか」**を切り分けます。

### `/client-side-redirect` → `/redirect-target` ― クライアント側ナビゲーション

中身が `location.replace("/redirect-target")` だけのページを返します。パース時点で走ります。

これは**キャプチャ側が `await` している最中に** JavaScript の実行コンテキストを破壊します。
Puppeteer はこれを
`Execution context was destroyed, most likely because of a navigation`
として表面化させ、その境界をまたいでページに触るコードは例外を投げます。
BrowserHive の `runOnStableContext` はこのために存在し、
このルートはそれが機能していることを示すためにあります。

**サーバ側の 302 では再現しません** ― ブラウザはページが存在する前にリダイレクトを追ってしまいます。
ページ自身がナビゲートする必要があります。

### `/lazy-images` ― 遅延されたサブリソース

3000px の詰め物のあと、画面外に画像が 2 枚。それぞれ**別の仕組み**で遅延されています。

- `<img loading="lazy">` ― ブラウザ自身による遅延
- `IntersectionObserver` が `data-src` を差し替える形

**スクロールしない限りどちらもリクエストされません。**
スクロールせずに取ったアーカイブは両方を欠きますが、
やっかいなのは**それでも一見まともに見える**ことです ―
HTML は正しく、エラーも無く、ただリプレイ時に画像が 404 になるだけです。

仕組みを 2 つ置いているのは、**壊れ方が違う**からです。
ネイティブの `lazy` はビューポートに反応し、observer はレイアウトに反応します。
一気に最下部までスクロールする実装は、片方を満たしてもう片方を取り逃します。

### `/cookie-banner` ― 固定オーバーレイ

コンテンツの下部に `position: fixed` のバーが固定されており、
クッキー通知と、それを消す Accept ボタンが載っています。

オーバーレイをどう扱うにせよ ― 除去する、無視する、貫通してクリックする ―
**確実にオーバーレイが存在するページ**があることで、
「対処できている / できていない」の差がスクリーンショットに現れます。

### `/cookie-and-storage` ― ページをまたいで残る状態

HttpOnly クッキー `meadow=1` を設定し、**同時に** `localStorage` にも書き込みます。

2 つ書くのは、**クリアされる仕組みが別**で、片方しか消さないリセットでは
もう片方が残るからです。この漏れは実害があります ―
ワーカーはキャプチャをまたいでブラウザを使い回すので、
タスク N の状態がタスク N+1 のアーカイブに現れます。
しかも**エラーとしてではなく、コンテンツとして、静かに**現れます。

## パラメータ付きのルート

### `/slow-response?delayMs=` ― ページロードのタイムアウト

`delayMs` 待ってから応答します。**既定値は 35000** で、
BrowserHive の 30 秒のページロードタイムアウトより意図的に大きくしてあります。
つまり `scenarios.slowResponse()` を引数なしで呼ぶと、すでにタイムアウトです。

遅延の位置に注意してください ― **応答の「前」**であって、応答中ではありません。
ソケットは開いたまま何も来ない、素朴な fetch が永遠にハングする状況です。
「始まってから止まる」応答が要るなら `/slow-body` を使います。

### `/block-main-thread?holdMs=&repeatForMs=` ― 応答しなくなるページ

ページのメインスレッドを `holdMs` ずつ保持する動作を、`repeatForMs` のあいだ
繰り返します。保持されているあいだ、ページの中では何も動きません ―
`setTimeout` のコールバックは発火せず、注入された `page.evaluate` は
実行されることすらできません。

**「ネットワークが遅い」とは別物です。** `/slow-response` が遅らせるのは**応答**であって、
最終的に返るページは普通に動きます。こちらは応答が即座に返り、**ページのほうが
止まります**。遅い応答でしかテストしてこなかった利用側は、ページ内の操作を守る
タイムアウトを一度も発火させたことがありません ― 発火させる手段が無かったからです。

このルートはそのために存在します。BrowserHive はブラウザ操作のひとつひとつを
「**この 1 操作が固まっていないか**」を問う予算で包んでいますが、その予算は
「実際に発火する」ことが示されるまでほとんど何も保証しません。とくに
`operationDelayMs` が効いている状態でも発火し続ける必要があります ―
意図的に遅くしたキャプチャは、無限に走ってよいキャプチャではないからです。

**パース中には保持しません。必ず `setTimeout` 経由で始めます。** パースを塞ぐと
`DOMContentLoaded` 自体が遅れ、コストが利用側の**ナビゲーション**の予算
（BrowserHive では 30 秒）に乗ってしまいます。狙いたいのはページ内の作業を包む
もっと短い予算（5 秒）のほうで、同じページに見えて試験しているものが別になります。

`repeatForMs` は 30000 で頭打ちにしてあります。スレッドを永久に保持するページは、
それを要求したキャプチャより長く生き残り、同じタブで次に走るものを巻き添えにします。

### `/http-status/:code` ― 非 2xx の分岐

指定したステータスをそのまま、本文つきで返します。
`/http-status/404`、`/http-status/503`、`/http-status/418`、何でも。

**本文があることに意味があります。** ステータスしか見ない実装にとっては全部同じですが、
応答をキャプチャする実装は
**「エラーページは保存する価値のある成果物なのか」**を判断する必要があり、
その判断には実物の本文が要ります。

### `/server-redirect-chain/:hops` ― リダイレクトの連鎖

長さ `n` の 302 チェーンで、最後は `/redirect-target` に着きます。
`/redirect/3` は 4 ホップです（`3 → 2 → 1 → 0 → /redirect-target`）。

長さをパラメータにしているのは、
**リダイレクト処理は 1 ホップではなく上限で壊れる**からです。
ブラウザは 20 前後で打ち切ります。
上限を超える長さを指定できることが、
真ん中ではなく**境界**を試せるということです。

### `/large-body?bytes=` ― 応答サイズの上限

ちょうど `bytes` バイトの本文を一度に送ります。既定は 1 MiB。

アーカイバは保存量に上限を設けないと、動画 1 本でディスクを食い潰します。
このルートは**上限の 1 バイト下と 1 バイト上**の両方を試せるようにします。

### `/slow-body?bytes=&overMs=` ― 遅い本文

`bytes` バイトを、およそ `overMs` かけて 10 分割で少しずつ送ります。

`/slow-response` とは**失敗の種類が違います**。こちらは**応答がすぐ始まって**から、ゆっくり届きます。
ヘッダは届き、ステータスは 200 で、
「リクエスト開始から測るタイムアウト」と「チャンク間隔で測るタイムアウト」が別の挙動になります。
**「応答が来た＝終わった」と扱う実装は `/slow-response` を通過して `/slow-body` でハングします。**

### `/fails-then-succeeds?failTimes=&key=` ― 決定論的なリトライ

`key` を伴う最初の `failTimes` 回は 503 を返し、以降はすべて 200 を返します。
既定は `fail=2`、`key=default`。

**リトライのテストを信用できるものにしているのは `key` です。**
失敗カウンタは key ごとに独立しているので、
同時に走る 2 つのテストが互いの予算を食い合いません。
同じプロセスで再実行するテストも、新しい key を使えばカウントがきれいな状態から始まります。
これが無ければ「リトライは効いたか」の答えが**実行順に依存**します
― 不安定さをテストしているつもりの、典型的な不安定テストです。

**key はスイート単位ではなくアサーション単位**で切ってください。

```ts
scenarios.failsThenSucceeds(2, "retry-budget-exhausted")
scenarios.failsThenSucceeds(1, "single-retry-then-success")
```

### `/assets/*` ― 静的サブリソース

`site/`（`hero.svg` / `below.svg`）を配ります。
`/lazy-images` から参照されるほか、
**バイト列が予測できるサブリソース**が欲しいときに直接使えます。

## イントロスペクション

テスト専用のエンドポイントが 2 つ。
**「何回リクエストされたか」こそが本当のアサーション**であることが多いために存在します
― 最終ステータスしか見ないリトライテストは、
1 回のリトライと 5 回のリトライを区別できません。

### `GET /__request-counts`

URL ごとのリクエスト回数を、素のオブジェクトで返します。

```json
{ "/plain-html": 1, "/fails-then-succeeds?failTimes=2&key=retry-budget": 3 }
```

キーは**クエリ文字列を含む完全な URL** です。
つまり `/fails-then-succeeds?failTimes=2&key=a` と `/fails-then-succeeds?failTimes=2&key=b` は別々に数えられます ―
失敗カウンタと同じ分離が、ここでも効きます。

### `POST /__reset`

リクエスト件数と失敗カウンタを両方クリアします。

**スイートごとではなく、テストごとに**呼んでください。
どちらのカウンタもサーバプロセス内にあるので、
実行全体で 1 つのコンテナを共有すると状態が積み上がります。
リセットしなければ、前のテストのヒットと今回のヒットは区別がつきません。

```ts
beforeEach(async () => {
  await fetch(`http://${meadowIp}:8080/__reset`, { method: "POST" });
});
```

### `GET /health`

`{ "ok": true }` を返します。**`scenarios` には含まれていません** ―
テストがアサートするものではなく、起動時にコンテナを待つためのものだからです。

```sh
until curl -sf "http://${MEADOW_IP}:8080/health" >/dev/null; do sleep 1; done
```

### `GET /__version`

いま応答しているのがどのビルドか。

```json
{ "version": "0.5.0", "revision": "abc1234", "buildTime": "2026-08-01T03:12:44.108Z" }
```

`/health` とは意図的に分けています。あちらは「生きているか」を問うもので、
起動待ちのループから短い間隔で叩かれます。こちらが答えるのは「これはどの
meadow か」― テストが理由の見えない落ち方をして、目の前のコンテナは
そもそも焼き直されたのか、と疑い始めたときに訊く問いです。

**効くのは `revision` です。** タグはリリース時にしか動かないので、開発中は
どのビルドも同じ `version` を名乗ります。`revision` はコミットごとに変わるので、
利用側が pin している submodule と突き合わせれば、焼き直し忘れたコンテナが
そこで捕まります。

```sh
running=$(curl -s "http://${MEADOW_IP}:8080/__version" | jq -r .revision)
pinned=$(git -C meadow rev-parse --short HEAD)
[ "$running" = "$pinned" ] || echo "meadow が古い: $running vs $pinned"
```

`GIT_TAG` / `GIT_REV` を渡さずに焼いたイメージは `version` が `unknown`、
`revision` が `dev` になります。これは失敗ではなく、**そのビルドが由来を
記録していない**という報告です ― 古さが見過ごされるのは、まさにその状態です。
